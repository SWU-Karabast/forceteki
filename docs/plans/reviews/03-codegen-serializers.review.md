# Adversarial Review — Plan 3: Codegen State Serializers

## Verdict

The plan's factual claims about both prior-art branches check out almost everywhere I could test them — the 687-line generator, `resolveStateNodeFromCallExpression`, the `MODULE_NOT_FOUND` swallowing, the `UndoSafeRecord` assert against the deleted state bag, the v2 single-commit cutover with no parity test, the build-script integration, the benchmark harness, and the drift counts (296/279 commits) are all real. The problem is not the history; it is that the plan **cherry-picks v2's decorator model (marker-only, delete the Undo wrappers) while claiming -morph as the superseding reference, and -morph kept those exact mechanisms on purpose** — for hasRef latching and for the delta hooks Plan 4 depends on. The result is an internally contradictory design ("no accessor override" vs. "generated setters" that nothing generates), a Phase A that is billed as "no behavior change" but cannot pass its own parity gate without an unscheduled `StateWatcher` refactor, and a loud-failure story (`assertStateAccessorContext`) that does not actually detect the failure mode it is claimed to catch. These are fixable, but three downstream plans inherit whichever answer this plan gives, so they must be fixed in the document before work starts. **Rejected pending revision.**

## Blocker

### B1. "Generated setters" don't exist in this design, and Plan 4 depends on them

**What the plan says:** Goal: "Field decorators become type-level markers only (validation via `assertStateAccessorContext`, no accessor override)" and "Delete the `UndoArray`/`UndoMap`/`UndoSet`/`Proxy` collection wrappers from the hot path." Then Non-goals: "the generated setters are written knowing Plan 4 will add a dirty-tracking hook; keep setter emission centralized in the generator so that is a one-place change." And the header: "Unblocks: Plan 4 (delta hooks live in generated setters)." Plan 4 (`docs\plans\04-delta-snapshots.md:18-22`) doubles down: "Every generated state setter **and collection mutation** calls `deltaTracker.recordFieldChange(...)`."

**What the code shows:** The generator on both branches emits *serializer functions*, not setters (`scripts/generate-state-serializers.ts` on both branches — `serialize<Class>`/`deserialize<Class>`/`registerStateSerializers`). Setters exist in exactly one place on the prior art: the **runtime decorator overrides**, which -morph deliberately kept — `statePrimitive`, `stateRef`, `stateRefMap`, etc. on `feature/quick-undo-deltas-morph:server/game/core/GameObjectUtils.ts` all return `set()` overrides calling `this.game.deltaTracker?.recordFieldChange(...)`, and the `UndoMap`/`UndoSet`/`UndoArray` wrappers are retained there specifically so **in-place collection mutations** hit the tracker (`UndoMap.set` at line ~452 calls `markStateRef` + `recordFieldChange`). v2 (`experimental/ts-morph-v2:server/game/core/GameObjectUtils.ts:149-219`) is the marker-only version — and v2 has no delta system.

**Why it matters:** If decorators are pure type-level markers with native backing fields, there is *no hook point anywhere* for Plan 4's dirty tracking — not for scalar writes and especially not for collection mutations. You cannot bolt setters on from a generated external module without runtime prototype patching, which is just the decorator system again with worse ergonomics. This is the load-bearing interface between Plans 3 and 4 and the two documents currently describe incompatible worlds.

**Fix:** Pick one explicitly: (a) adopt -morph's actual model — decorators keep *thin* setter overrides (`deltaTracker?.recordFieldChange` + eager ref marking, no state-bag dual-write) and the ref-collection wrappers survive as the mutation hooks; or (b) truly marker-only, and Plan 4's mechanism is rewritten to not be setter-based. Then fix the "Unblocks" line, the Goal bullets, and Plan 4's "Mechanism" section to agree. Option (a) is what the best-of-line branch proved; the plan should say why it deviates if it does.

### B2. Phase A is not "no behavior change": `StateWatcher` / `CopyMode.UseBulkCopy` will fail parity on every game, and the required refactor is unscheduled

**What the plan says:** "Phase A — Generator + parity gate (no behavior change)… scan `@registerState`/`@registerStateBase` classes and decorated `accessor` fields." The plan never mentions `StateWatcher`, `CopyMode.UseBulkCopy`, or `state.entries`.

**What the code shows:** `C:\Users\cdmay\OneDrive\Documents\Github\forceteki\server\game\core\stateWatcher\StateWatcher.ts` is `@registerStateBase(CopyMode.UseBulkCopy)` (line 33) and stores its entire payload by **writing the state bag directly** — `this.state.entries = []` (line 55), `this.state.entries = updatedStateValue` (line 131), via `protected declare state` (line 40). There is no decorated accessor for `entries`, so a generator that scans decorated fields emits an empty serializer for every watcher, and the Phase A parity compare (`getStateUnsafe()` contains `entries`, generated record doesn't) fails immediately. Both prior branches hit this and solved it identically: v2's cutover commit (`git show 7e6545fd7 -- server/game/core/stateWatcher/StateWatcher.ts`) converts it to `@stateValue() private accessor entries: TState[] = []` and introduces a new `CopyMode.CompileTime`; -morph carries the same change. The plan claims to have mined both branches' gaps but missed the one refactor both branches were forced to make.

**Why it matters:** Phase A's whole justification is "riskless to land," but it has a hidden prerequisite PR that touches restore semantics for watchers (bulk-copy vs. field-copy) — exactly the kind of change that should go through its own review, and possibly through Plan 1's hygiene track. Also, `copyState`'s `bulkCopyMetadata` branch (`server\game\core\GameObjectUtils.ts:222-227, 731-733`) has to be explicitly retired or the two systems diverge.

**Fix:** Add a Phase A step 0: migrate `StateWatcher.entries` to a decorated accessor (port the branches' change), decide the fate of `CopyMode.UseBulkCopy`, and audit for other direct `state` writers (`TokenCards.ts` `declare state: never` at lines 20/36/45 is the only other `declare state` and is inert). Note that watcher `entries` are arbitrary `TState[]` — plain objects containing `GameObjectId` strings (enforced dev-only in `StateWatcher.addUpdater`, lines 91-112) — so the generic `stateValue` encoder is what serializes them; call that out.

### B3. The claimed safety net for generator-missed fields does not work

**What the plan says:** Risks: "keep `assertStateAccessorContext` so a field the generator missed still fails loudly at startup in dev" (and Goal: "validation via `assertStateAccessorContext`").

**What the code shows:** `assertStateAccessorContext` doesn't exist on main at all (grep: no matches); on both branches it is only the static/private/symbol guard (`experimental/ts-morph-v2:server/game/core/GameObjectUtils.ts:44-51`). It validates the *decorator call site*, not generator coverage. A field the generator misses — a decorated accessor added to a card implementation under `server\game\cards\**` (none exist today, but nothing prevents it; `buildAutoInitializingCardClass` happily wraps such a class), a class expression the static resolver can't follow, or a new mixin pattern — passes `assertStateAccessorContext` and is then **silently dropped from every snapshot**. That is precisely the "silent degradation" the README's invariant 4 forbids, and it's more insidious than the `MODULE_NOT_FOUND` swallowing the plan correctly condemns in gap 2.

**Fix:** Specify a real cross-check: decorators keep writing field-name metadata (cheap, they already do via `context.metadata`), and at startup (or in a spec that instantiates every registered class) compare the runtime metadata field set against the generated serializer's field set per class; hard-fail on any delta. This also gives you the staleness detection that "emit a content hash the runtime verifies" hand-waves at — note that a source-content hash cannot be re-verified at runtime in a compiled production build where the TS sources aren't present; the metadata-vs-generated comparison can.

## Major

### M1. Marker-only decorators change `hasRef` latch timing, which controls snapshot retention

On main, every ref-decorated setter eagerly calls `getObjectId()` on stored values (`server\game\core\GameObjectUtils.ts:417, 438, 479, 523, 565, 606` via `createIdArray`/`createIdMap`/etc.), which latches `_hasRef` (`GameObjectBase.ts:154-166`). `GameStateManager.buildGameStateForSnapshot` (`GameStateManager.ts:136-141`) calls `removeUnusedGameObjects()` **before** serializing, trusting that latch. Delete the setter overrides and nothing latches at write time; an object referenced by another object's field but never explicitly `getObjectId()`'d gets culled at the next snapshot, and the referencing object's serialized ref then dangles → `getFromUuidUnsafe` → `SevereHaltGame` on rollback. -morph understood this: it kept eager `markStateRef` in every setter *and every wrapper mutation* (`markStateRef` at `feature/quick-undo-deltas-morph:server/game/core/GameObjectUtils.ts:66-78`) *and* flipped the snapshot order to serialize-then-remove (`GameStateManager.ts:146→149` on that branch, vs. remove-then-serialize on main). The plan mentions none of this. **Fix:** document the latch contract explicitly, keep eager marking (see B1 option a) or move latching to serialize time with the order flip — and note the order flip is itself a parity-visible behavior change (which uuids appear in `states`).

### M2. The Phase A parity gate never exercises the deserialize path, but Phase B decisions are deferred to it

Phase A's harness "runs both … paths, normalizes … and deep-compares" — serialize only. Yet B.3 says "Include -morph's zone-membership reconciliation if parity testing shows it is needed on main." A serialize-compare cannot show that; `reconcileUpdatedCardZoneMemberships` (`feature/quick-undo-deltas-morph:server/game/core/snapshot/GameStateManager.ts:306,368`) exists because of *restore-side* effects. So the deserializers — the half of the generated code that mutates live state through a completely different mechanism than `copyState`'s hydrator walk (`server\game\core\GameObjectUtils.ts:728-792`) — get their first real exercise at cutover, which is structurally the same gamble v2 took. **Fix:** add a restore-parity leg to Phase A: after each rollback in the undo suite, (or in a dedicated harness) restore a shadow copy via the generated deserializers and compare resulting field values against the old-path restore; alternatively run the full undo suite twice, once per restore path, behind a flag. Also state that the parity harness must be side-effect-free (read refs via `.uuid`, never `getObjectId()`, since `getObjectId` mutates `_hasRef` and asserts).

### M3. Deserialize-side copy semantics are unspecified, and the current design depends on them

The plan pins copy semantics for *serialization* ("Copy semantics must match today's v8-clone (no aliasing of live collections into stored records)") but says nothing about restore. Today every rollback gets fresh objects from `v8.deserialize` (`GameStateManager.ts:152-154`), snapshots are rolled back to repeatedly (including the nested `beforeRollbackSnapshot` recovery at lines 190-199), and the code explicitly relies on state-object freshness: "Rollback swaps the entire state object reference, so retaining the previous object here is safe" (lines 163-164). With plain record maps held in `IGameSnapshot.states`, a generated deserializer that assigns `record.someArray`/`record.decklist` by reference hands live mutable state a pointer into the retained snapshot — the second rollback to that snapshot restores corrupted data. -morph got this right (`deserializeStateValue` = `structuredClone`, `StateSerializers.ts`). **Fix:** one sentence in B.3: "deserializers must never alias values out of the stored record; all non-primitive values are cloned/decoded to fresh objects," plus a spec: roll back to the same snapshot twice with mutation in between, assert identical results.

### M4. The lifecycle hooks' `oldState` argument: format change and hidden per-rollback serialization cost

`afterSetState`/`afterSetAllState`/`cleanupOnRemove` all take the pre-rollback state bag (`GameStateManager.ts:165-178, 216`). After the bag is deleted, `oldState` must be *manufactured* — v2 did it by running the generated serializer on every live object during rollback (`experimental/ts-morph-v2:server/game/core/snapshot/GameStateManager.ts:180`), an O(all objects) serialize pass per undo that main currently avoids by design (the "avoids a structuredClone" comment). The plan's B.3 says "Preserve the lifecycle contract exactly" without saying where `oldState` comes from or that its shape changes from live-bag (Maps, `GameObjectId` Maps) to JSON-safe tagged records. I verified every current consumer reads only primitives off `oldState` (`AbilityLimit.ts:38-52`, `TriggeredAbility.ts:316-330`, `OngoingEffectEngine.ts:44-58`, `Damage.ts:149-152`, `StateWatcher.ts:148-150`, `OngoingEffect.ts:205` ignores it) — so the format change is survivable *today*, but it's an API contract change that must be documented, and the serialize-pass cost must show up in the Phase B benchmark comparison or the "replace runtime cost" headline is overstated for the rollback path. **Fix:** specify the `oldState` source and format in B.3; add "rollback time" to the benchmark metrics (it's already listed as "restore time" — make sure it includes the oldState serialize pass).

### M5. Class-name-keyed registry vs. mixin factories: names are not unique identities

The registry (`registerStateSerializers`, resolved by walking `constructor.name` up the prototype chain — `feature/quick-undo-deltas-morph:server/game/core/StateSerializers.ts:96-110`) is keyed by class name, and the plan hands this to Plan 5 as "the class-identity infrastructure recreation needs." But mixin factories mint a **new class per call with the same name**: `AsUnit`, `WithDamage`, `WithCost`, `WithStandardAbilitySetup` etc. (`server\game\core\card\propertyMixins\*.ts`, e.g. `UnitProperties.ts:116`, `Damage.ts:30`) each exist multiple times with *different flattened ancestor chains* (leader vs. non-leader unit chains). A flattened serializer keyed "AsUnit" is ambiguous; it only works if the registry's key set is restricted to concrete exported classes whose names are globally unique, with mixin fragments never registered as lookup targets — and the generator must **fail on duplicate registered names with non-identical field sets** (today it would emit two `export const serializeAsUnit` and not even compile, which is at least loud, but the policy should be stated, not accidental). For Plan 5, which wants name → constructor recreation, name-ambiguity of mixin classes is a real hazard. **Fix:** add a "registry key policy" paragraph: keys are concrete `@registerState`/exported classes; generator enforces uniqueness; mixin fragments are an internal generator concept only.

### M6. Generator cost and the fast/incremental dev loop are unaddressed

The generator loads the entire tsconfig project (`new Project({ tsConfigFilePath: 'tsconfig.json' })`, then `getSourceFiles('server/**/*.ts')` — both branches), which includes thousands of card implementation files, via ts-node, on **every** `npm test` / `npm run dev` (build scripts run unconditionally: `scripts\build-test.js`, `scripts\build-dev.js`). Meanwhile `npm run test-fast` (`build-test.js --fast-build`, lines 11-25) exists specifically to skip work — prepending an unconditional whole-project ts-morph pass taxes exactly the loop it protects, and *skipping* it in fast mode leaves a stale gitignored artifact that tsc will happily compile (test tsconfig includes `../server/**/*`). The plan's only stale-artifact mechanism is the unverifiable runtime content hash (see B3). **Fix:** specify a generation cache (hash the decorated-source file set; skip regen when unchanged — cheap because the candidate file set can be found with a text scan before instantiating ts-morph), define behavior under `--fast-build`, and record the generator's wall-clock cost as a Phase A acceptance number alongside the snapshot benchmarks. Also note the ts-morph↔TypeScript version coupling (repo pins `typescript ^5.5.4`; ts-morph releases lag TS syntax) as a named maintenance risk — the "Risks" section currently omits ts-morph entirely.

## Minor

1. **CI lint job breaks on a gitignored non-optional import.** `.github\workflows\pullrequest.yml:24` runs `npx eslint --quiet` with no build/generation step. The plan's recommended "make the import non-optional" + gitignored artifact means `eslint-plugin-import-x` (with the TS resolver, both in `package.json`) sees an unresolved module on every PR. Either the lint job generates first, or the generated path is carved out of the resolver — say which.
2. **`undefined` vs. `null` parity mismatches are guaranteed.** Main's bag stores `newValue?.getObjectId()` (`GameObjectUtils.ts:606` → `undefined` possible); prior-art generated encoders emit `?? null` (`experimental/ts-morph-v2:server/game/core/StateSerializers.ts:59`); hydrators already collapse `rawValue == null → null` (`GameObjectUtils.ts:107-167`). The Phase A normalizer must define null/undefined equivalence up front or the gate drowns in false positives on day one.
3. **`stateValue` encoding must be recursive and must hard-fail on unknown types.** The plan lists top-level shapes only, but real `stateValue` payloads include `Map<string, string[]>` (`GainNonKeywordAbilitiesFromUnitEffect.ts:18-20`), nested plain objects (`Player.ts:155` `_decklist`), and `stateValue`'s documented contract is "structuredClone-compatible" (`GameObjectUtils.ts:619-637`) — a strictly larger set than JSON (Date, RegExp, typed arrays are legal today). Per invariant 1, the encoder should throw on anything it can't tag-encode, and the plan should schedule an audit of current `stateValue` payloads. Related nit: in-memory records can hold `NaN`/`Infinity`, which are "JSON-representable" only until someone actually calls `JSON.stringify` — Plan 6 will care.
4. **Phase B must repoint the `I*State` interfaces.** `ITriggeredAbilityState`, `IAbilityLimitState`, `ICustomDurationEventState`, `IStateWatcherState` (e.g. `AbilityLimit.ts:23-25`) are typed views of the bag used in `afterSetState` signatures; deleting `IGameObjectBaseState`-as-bag orphans them. Gap 5 treats `ISerialized*` interfaces as optional generator polish, but *something* must type the lifecycle-hook argument post-cutover; these two decisions are the same decision.
5. **Gap 3 is slightly misstated.** On -morph the `readonly` argument of `stateRefArray` is honored at *runtime* (the retained decorator setter wraps or doesn't — `feature/quick-undo-deltas-morph:server/game/core/GameObjectUtils.ts`, stateRefArray branch); it's only the *generator's* field model that flattens both to `'refArray'` (`STATE_FIELD_DECORATORS`, line ~57). The distinction only fully disappears under this plan's marker-only design — i.e., the plan's own choice creates the bug it attributes to the branch. The mutable-array users are hot paths: `DeckZone.ts:22,25` and `GameObject.ts:30`.
6. **`Game.state` ref-fields make the "may stay v8-serialized" option mildly inconsistent.** `IGameState` (`SnapshotInterfaces.ts:136-149`) is already JSON-safe (GameObjectId strings), so the recommended uniform-record option is nearly free; say that, and pin the decision rather than leaving "may."
