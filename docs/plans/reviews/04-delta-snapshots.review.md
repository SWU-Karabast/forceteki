# Adversarial Review — Plan 4: Delta Snapshots

## Verdict

The plan's forensic claims about the prior art are almost all accurate — I verified the first-write-wins bug exactly where claimed (`feature/quick-undo-deltas:server/game/core/snapshot/DeltaTracker.ts`, `recordFieldChange` unconditionally overwrites `goEntry[fieldName]`), the per-window full serialization on that branch, the `Buffer.alloc(0)` sentinels, the 2,325-insertion/zero-test diff, the 1555-line plan doc with its "Restart Requirements" section, -morph's `MaxDeltaEntries = 3`, its +43-line `SnapshotTypes.spec.ts` regression case, and `GameState.ts` (161 lines by `wc`, plan says 162 — immaterial). The mandated `if (fieldName in goEntry) return;` guard plus a dedicated test genuinely fixes the known bug rather than reinheriting it. But the plan has four structural problems: **(1)** its interface to Plan 3 is stale in three places ("generated setters" no longer exist in Plan 3's revised design); **(2)** its one concrete deviation from -morph's chain machinery — "per-container ordered-list chain selection" — is based on a misattribution (**-morph uses the exact same global filter scheme the plan condemns**) and, as written, would produce corrupt rollbacks in any two-player game; **(3)** the Restore section omits the three load-bearing pieces of -morph's rollback path (pending-window delta, tracker suspension, recovery-snapshot materialization) — including the piece that serves the *most common* undo case; and **(4)** its other deviation from -morph, "manual snapshots always full," silently guts its own headline verification gate, because `ENABLE_UNDO_ALL_TESTS` replays every spec through a *manual* rollback, and -morph made manual snapshots delta-backed precisely so that gate would exercise chains. **Rejected pending revision** — the mechanism -morph proved is sound, but the plan's two departures from it are each wrong in a way that would pass review and fail in production.

## Blocker

### B1. Stale Plan-3 interface: "generated setters" no longer exist (confirmed drift, full extent mapped)

**What the plan says:** Header: "Depends on: Plan 3 (dirty-tracking hooks live in the generated setters; ...)" (line 4). Mechanism: "Every generated state setter and collection mutation calls `deltaTracker.recordFieldChange(gameObject, fieldName)`" (lines 17-20). Open issues: "**If** Plan 3 did the `stateMap`/`stateSet` decorator split, mutation methods hook the tracker; if not, that split becomes a prerequisite here" (lines 84-85).

**What Plan 3 (revised) and the code show:** Plan 3's "Decorator model after cutover" (`docs\plans\03-codegen-serializers.md:98-126`) pins the -morph model: hooks live in **retained runtime decorator setter overrides** and the surviving `UndoArray`/`UndoMap`/`UndoSet` wrappers; the generator emits only serializer functions. That matches the branch: every hook on `feature/quick-undo-deltas-morph:server/game/core/GameObjectUtils.ts` is a runtime decorator `set()` override (lines 195, 230, 243, 266, 292, 317, 340, 363) or a wrapper mutation method (`UndoMap.set/delete/clear` at 456/462/467, `UndoSet` at 497/503/508, `UndoArray` at 537-570), all calling `recordFieldChange` **before** the mutation. Nothing generates setters on any branch. Additionally, the conditional in lines 84-85 is stale: Plan 3 Phase B step 7 now *commits* to the `stateMap`/`stateSet`/`stateArray` split in-phase, so Plan 4 should state "done in Plan 3 B7 — verify present," not "if."

**Full extent of the drift — and what is *not* drifted:** The three spots above are the whole of it. The rest of the mechanism section is consistent with revised Plan 3: pre-write capture "through the generated per-field serializer" matches Plan 3's "per-field encoders individually addressable" non-goal note and -morph's `getStateDeltaSerializer`; "write each recorded old value back through the generated field deserializer" matches `rollbackToDeltaChain`; the `UndoSafeRecord`/`go.state` note (lines 86-87) matches Plan 3 gap 4; "Object creation is hooked in `GameStateManager.register`" matches -morph's `register` (calls `recordObjectCreation`, correctly inside the `!_disableRegistration` guard).

**Fix:** Rewrite line 4 to "dirty-tracking hooks live in the retained decorator setter overrides and collection wrappers (Plan 3, 'Decorator model after cutover'); the generator emits the per-field serializers deltas reuse." Rewrite lines 17-20 to "every retained decorator setter and every `Undo*` wrapper mutation method calls `recordFieldChange` before the write." Replace the lines 84-85 conditional with a hard dependency on Plan 3 B7.

### B2. The chain-selection directive misattributes -morph's design and the proposed replacement is incorrect for interleaved two-player windows

**What the plan says:** "Chain selection must be per-container ordered-list based, not the global `filter(id > target && id <= current)` scheme from `quick-undo-deltas` (fragile once ids interleave across containers)" (lines 46-48), in a section titled "Mechanism (adopted from `-morph`)."

**What the code shows:** -morph — the branch whose design the plan claims to adopt — uses the **identical global filter**: `rollbackToDeltaSnapshotId` builds `chain = Array.from(this.deltaSnapshotsById.values()).filter((delta) => delta.id > targetSnapshotId && delta.id <= currentSnapshotId).sort((a, b) => b.id - a.id)` (`feature/quick-undo-deltas-morph:server/game/core/snapshot/SnapshotManager.ts`, ~lines 250-252; byte-for-byte the same filter as `quick-undo-deltas` lines 241-243). And the global scheme is not an accident — it is **required**: delta windows are global time slices (one tracker per game), but each delta lands in only the *acting player's* `DeltaSnapshotContainer` (`takeSnapshot` Action case). Rolling player A back two actions must unwind the opponent's intervening windows, which exist only in the global `deltaSnapshotsById` index and in B's container. A per-container ordered-list chain, as the plan directs, would skip B's windows and every bridge delta (bridges go into the global index only, never into any container — `checkpointDelta` line 225 vs. 227-231) and silently restore corrupt state.

**The real fragility the plan should be naming:** (a) the filter has **no contiguity check** — if any intermediate delta is absent, the chain silently has a hole; (b) `deltaSnapshotsById` is **never evicted by age** (only `pruneDeltaSnapshotIndex` removes *newer* ids on rollback), which is simultaneously what makes the filter safe on -morph and an unbounded memory leak over a long game — directly contradicting the plan's "smaller retained-snapshot memory" headline. The moment you add the eviction the memory claim requires, holes become possible and the missing contiguity check becomes a corruption bug.

**Fix:** Replace the directive with: chains are selected from a single global, id-ordered delta index (containers hold per-player *entry points*, as in -morph); chain application **hard-fails** unless the selected chain covers every snapshot id in `(target, current]` (invariant 4); the index evicts deltas older than the oldest delta-backed target still reachable from any container (and state that manual pinning must not defeat this — see B4).

### B3. The Restore section omits the pending-window delta, tracker suspension, and recovery-snapshot materialization — three load-bearing mechanisms, one of which serves the most common undo

**What the plan says:** Restore = "roll back ... by applying the delta chain newest-first: for each delta, restore RNG + `lastGameObjectId`, write each recorded old value back ..., remove objects in `createdObjectUuids` ..., then run the standard lifecycle pass ... and `reconcileUpdatedCardZoneMemberships`" (lines 36-41). Nothing else.

**What the code shows, three omissions:**

1. **The pending-window delta.** The current action's mutations live in the *un-checkpointed* live tracker, not in any stored delta. -morph prepends them: `chain.unshift(this.#game.deltaTracker.createPendingRollbackDelta())` (`rollbackToDeltaSnapshotId`). For the single most common undo — revert the current action, `QuickRollbackPoint.Current`, target id == current id — the filtered chain is **empty** and the entire rollback is the pending delta. A plan whose restore description doesn't contain this concept describes a mechanism that cannot perform its primary use case.
2. **Tracker suspension and restart.** Delta restore writes via `(go)[fieldName] = fieldSerializer.deserialize(...)` — i.e., **through the hooked decorator setters**. -morph calls `deltaTracker.stopTracking()` at the top of `rollbackToInternal` and `startTrackingFromCurrentSnapshot()` after (both success and failure paths). Without this, the restore pollutes the tracker (and first-write-wins makes the pollution *sticky*: the pre-restore value gets locked in as "window start"). The plan never mentions it.
3. **Recovery-snapshot materialization.** Main's nested-recovery contract passes the current full snapshot as `beforeRollbackSnapshot` (`SnapshotContainerBase.ts:72`, `GameStateManager.ts:190-199` on main). Under deltas, the current snapshot is hollow — -morph must serialize **live state** on every delta rollback (`createRecoverySnapshot()` before `rollbackToDeltaChain`), and after success replaces the current snapshot with a hollow entry that lazily rematerializes (`updateCurrentSnapshotFromDelta` → `states: {}`; `getCurrentActionSnapshot` materializes on demand). This is a full O(all objects) serialize per rollback, the invariant-3 recovery story, and the mechanism behind the very regression spec the plan says to port — and none of it is in the plan.

**Fix:** Add a "Rollback protocol" subsection: stop tracking → build chain (global, contiguity-checked) → unshift pending delta → materialize recovery snapshot from live state → apply → replace current snapshot (hollow + lazy rematerialization contract) → restart tracking window. Add rollback wall-clock (including the recovery serialize) to the benchmark list.

### B4. "Manual snapshots: always full" silently guts the plan's own headline gate

**What the plan says:** "Manual snapshots: always full (they can outlive any delta window)" (line 57), and Verification: "Full suite + `ENABLE_UNDO_ALL_TESTS=true` (**the real gate** — every spec replayed through rollback)" (lines 111-112).

**What the code shows:** The whole-suite undo harness replays every spec via a **manual** snapshot rollback: `undoIt` takes `game.takeManualSnapshot(activePlayer)` at test start and rolls back with `{ type: SnapshotType.Manual, ... }` (`test\helpers\IntegrationHelper.js:50, 249-253`). On -morph, a manual snapshot taken at a delta timepoint is deliberately **delta-backed** (`takeManualSnapshot` → `manualDeltaSnapshots`; `rollbackManualSnapshot` → `rollbackToDeltaSnapshotId`) — which is exactly why -morph's whole-suite gate exercised delta-chain restore on every action-phase spec. Under Plan 4's rule, every replayed spec rolls back through the **full-snapshot path**; the delta restore machinery — the entire novel, dangerous surface of this plan — is exercised only by the half-dozen dedicated specs. The gate the plan calls "real" no longer gates the thing the plan builds. (To be fair to the plan: always-full manuals *do* solve a real problem — a delta-backed manual bookmark pins its entire chain in the global index forever, or dies when `MaxDeltaEntries` evicts a link. But the plan chose the policy without noticing what it does to the harness.)

**Fix:** Pick one and write it down: (a) keep always-full manuals **and** change the `undoIt` harness (or add a second `ENABLE_UNDO_ALL_TESTS` mode) to replay via the quick/action delta path; or (b) keep delta-backed manuals with an explicit pinning-vs-eviction policy. Either way, state explicitly what fraction of the gate traverses `rollbackToDeltaChain`.

## Major

### M1. No invariant-4 story: a missing or corrupted chain fails silently

-morph's `rollbackToDeltaSnapshotId` returns `null` when the target delta is absent (silent no-op undo for the user), and a missing *intermediate* delta produces a holed chain with no detection whatsoever — the filter yields whatever exists, and the restore quietly writes a wrong state. The plan's Verification section (lines 109-119) contains no corrupted-chain, missing-link, or hard-fail spec, despite the README's invariant 4 ("a failed parity check must hard-fail loudly") and despite the plan itself invoking that standard against Plan 3's `MODULE_NOT_FOUND` swallowing. **Fix:** contiguity assertion at chain-build time (every id in `(target, current]` present, else `SevereHaltGame`-class failure), plus a spec that deliberately deletes an intermediate delta and asserts the loud failure.

### M2. Objects created *during* rollback are invisible to delta tracking, and delta restore cannot remove them

`recordObjectCreation` is guarded by `if (!this._tracking) return;` and tracking is stopped during rollback (B3). Lifecycle hooks run arbitrary code — `cleanupOnRemove`, `afterSetState`, `afterSetAllState`, zone reconciliation — and main's own `GameStateManager.ts:35-36` comment ("unused for now but will be used to detect GO creation during the rollback process") acknowledges GO-creation-during-rollback as a live, unsolved concern. The full-snapshot path self-heals: culling is **absence-based** (object not in `snapshot.states` → removed). Delta restore is **presence-based** (`createdObjectUuids` only) — an object registered mid-rollback is in no delta's creation list and can never be removed by any later delta rollback: it leaks, and any refs it latched (`hasRef` is monotonic, `GameObjectBase.ts:154-166`) pin it into every subsequent full snapshot. **Fix:** decide and document: either hard-assert no registration while `_isRollingBack` (finally cashing in main's TODO), or record rollback-time creations into the freshly started window. Add a spec either way. (The created-then-*culled* case is handled fine: `checkpointDelta` runs `removeUnusedGameObjects()` per timepoint, and `rollbackToDeltaChain` tolerates missing uuids via `gameObjectMapping.get(uuid)`-then-skip — the plan could state this explicitly but it's not a gap.)

### M3. "Run the standard lifecycle pass" — the delta path's lifecycle is *not* standard, in order or in cost

On main, `afterSetState` fires inside `go.setState` during the update loop, *before* `cleanupOnRemove`, and `afterSetAllState` runs **only for updated objects** (`GameStateManager.ts:157-217`, `GameObjectBase.ts:110-115`). -morph's `rollbackToDeltaChain` defers `notifyAfterSetState` until after removals *and* zone reconciliation, then calls `afterSetAllState` on **every live object**, manufacturing `oldState` for untouched objects by serializing their *current* state — an O(all objects) serialize pass per rollback. That is a different ordering contract and a hidden cost the plan's "per-action cost drops to O(fields mutated)" framing never acknowledges (rollback also pays the recovery-snapshot serialize, B3). **Fix:** pin the authoritative lifecycle ordering for the delta path (and whether all-objects `afterSetAllState` is required — if it is, say why; `OngoingEffectEngine` is the likely reason), and add "delta rollback time" to the benchmark list, which currently measures only per-action snapshot time and heap (line 118-119).

### M4. Manual-snapshot anchor drift under lazy materialization

On main, a manual snapshot stores the **window-start** full snapshot (`takeManualSnapshot` → `SnapshotMap.takeSnapshot` → `getCurrentActionSnapshot`, which is the serialization taken at `moveToNextTimepoint`). Under deltas the current snapshot is hollow, and -morph's `getCurrentActionSnapshot` materializes **live** state via `createRecoverySnapshot()` — *labeled with the window-start id*. A manual snapshot taken mid-window (it's a player-triggered API — `Game.ts:1794` — not tied to `ActionWindow.ts:130-131`'s take-immediately-after-timepoint discipline) stores mid-action state under an action-start id: rollback lands somewhere that is neither. The ported -morph spec doesn't catch this because it takes the manual snapshot immediately after a rollback, when live ≡ snapshot. **Fix:** pin the anchor rule — e.g., manual snapshot at a delta timepoint forces a checkpoint of the pending window and takes a fresh full snapshot under a **new** id — and add a mid-window manual-snapshot spec.

### M5. Bridge entries double-consume snapshot ids and timepoint numbers, perturbing the confirmation policy

In -morph, every phase-boundary timepoint runs `checkpointDelta(timepoint, /* bridge */ true)` (consuming one snapshot id + timepoint number) *and then* `createSnapshotForCurrentTimepoint` (consuming another). Main's `opponentActedSinceLastSnapshot` classifies on `timepointsSinceSnapshot` being exactly 0/1/2 (`SnapshotManager.ts:457-474`) to decide whether quick undo needs opponent confirmation; inflating the count by one per boundary shifts those classifications near phase edges (toward requiring confirmation — a UX regression, not corruption, but an unexplained behavior change). The plan spends half a sentence on bridges (line 55-56) and none on this bookkeeping. **Fix:** either give the bridge and the full snapshot the same timepoint number (one timepoint, two artifacts), or document the inflation and adjust the `opponentActedSinceLastSnapshot` thresholds; add a boundary-adjacent confirmation-policy spec. This belongs inside the existing "phase-boundary prompts" open issue, which currently covers only the prompt/`getQuickRollbackPoint` side (and whose main-side citation, `SnapshotManager.ts:328`, I verified).

## Minor

1. **First-write-wins verdict: the plan's design does prevent the known bug — but the test is under-specified for collections.** Confirmed the bug (`quick-undo-deltas` `recordFieldChange`: unconditional `goEntry[fieldName] = this.snapshotValue(currentValue)`, so N writes → restore to pre-*last*-write value) and the -morph guard the plan quotes verbatim. The guard is sound *only* under the invariant "record strictly before mutate, at every hook site" — true at all ~20 -morph sites I checked, but nothing in the plan states the invariant. The dedicated spec ("mutate a field 3×") reads as scalar reassignment; the equally dangerous path is in-place collection mutation (`UndoMap.set/delete/clear`, `UndoArray.push/splice` — each records a serialized snapshot of the whole collection on first touch). **Fix:** state the pre-write ordering invariant in the Mechanism section and add a 3×-in-place-collection-mutation spec per wrapper type.
2. **Missing spec: interleaved two-player chain.** The Verification list (lines 113-117) has "multi-delta chain across 3 actions" but nothing guaranteeing the chain crosses the *opponent's* windows — the exact case B2's per-container design would break. Add it explicitly, plus "roll back to the same delta target twice with mutation in between."
3. **Plan 2 / load interaction:** one sentence needed — a loaded game re-enters at an action-window safe point with empty snapshot history; the delta tracker must start (or explicitly not start) a fresh window at that entry point.
4. **-morph implementation wart, don't port:** `recordFieldChange` does the serializer lookup + `Contract.assertNotNullLike` *before* the `fieldName in goEntry` early-return — per-write cost on the hot path for already-recorded fields. Reorder in the reimplementation.

## Nit

- `GameState.ts` on -morph is 161 lines by `wc -l`, not 162. Every other checkable number in the plan is exact: 1555-line plan doc ✓, 2,325 insertions / 0 test-file changes on `quick-undo-deltas` ✓, `SnapshotTypes.spec.ts` +43 ✓, `MaxDeltaEntries = 3` ✓, `Buffer.alloc(0)` sentinels (`quick-undo-deltas` `SnapshotFactory.ts:196-197`) ✓, main TODO at `SnapshotManager.ts:328` ✓, `alwaysTrackState` already exists on main (`GameObjectBase.ts:61-65`) so the `GameState` port is real ✓.

## What I'd ask the author

1. **Walk me through rolling player A back two actions in a game where player B acted in between.** Which data structure yields B's window deltas and the bridge deltas, what asserts the chain has no holes, and what evicts old deltas from that structure without creating holes? Your current text ("per-container ordered-list based") cannot answer this, and the branch you say you're adopting does the thing you forbid.
2. **After this plan lands, what percentage of `ENABLE_UNDO_ALL_TESTS` replays actually execute `rollbackToDeltaChain`?** If the answer is "only the dedicated specs" — because the harness rolls back via manual snapshots you've made always-full — is that an acceptable gate for the riskiest restore path in the codebase, and if not, which side moves: the manual-snapshot policy or the harness?
3. **Where do the current action's un-checkpointed mutations go when the user hits undo?** If the answer is -morph's pending-rollback delta plus stop/restart of the tracker, why is none of that in the Restore section — and if the answer is something else, what is it?
