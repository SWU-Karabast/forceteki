# Adversarial Review: Plan 5 — GameObject Release & Recreation

**Verdict: REJECTED (as currently written) — needs a revision pass before it can anchor Plan 6.** The plan's ground-truth survey is accurate (I verified essentially every file/line claim: `GameObjectUtils.ts:751`, `GameStateManager.ts:35-36/157-175`, `Card.ts:555-562/320/1143`, `GainAbility.ts:82`, `Player.ts:772`, `TriggeredAbility.ts:301`, the `alwaysTrackState` and `getGameObjectName` inventories all check out). The problem is that the plan's *mechanisms* stop exactly where the hard problems start. Three of those problems are load-bearing: (1) recreation requires registering GameObjects during rollback, which Plans 1B and 4 have already pinned as a hard-fail contract with a dedicated spec — the plan never reconciles this; (2) recreating a Card is not one construction but a transitive fan-out of side-effect constructions (abilities, limits, default actions) whose uuid reconciliation is unaddressed and whose "construct unlinked" step is structurally impossible under the auto-init wrapper; (3) the 5b closure-recipe scheme is provably insufficient for lasting effects, whose props are resolution-parameterized (`CardLastingEffectSystem.ts:113` literally builds `matchTarget: card` from the resolved target) yet survive snapshot boundaries — the plan's "out of scope" carve-out excludes only transients and claims the rest is derivable from card definitions, which the code contradicts. Additionally, the plan's own flagship 5a example (evict an `AbilityLimit`) is not recreatable from its state record as the code stands.

---

## Blockers

### B1. Recreation requires registration during rollback; Plans 1B and 4 have pinned "registration during rollback hard-fails" — the contradiction is never addressed

- **Plan says:** A2 "Allow explicit uuid assignment at registration … for the rehydration path"; A3 constructs missing instances inside the restore sequence. The intro even cites `_isRollingBack` as evidence the codebase "anticipates this."
- **Code/plans show:** Every GameObject constructor unconditionally registers (`GameObjectBase.ts:87` → `GameStateManager.register`, `GameStateManager.ts:79-96`). Plan 1 item B activates the `_isRollingBack` guard so `register()` **hard-fails during rollback** (01-snapshot-hygiene.md:142-146), and Plan 4 elevates this to "Rollback performs zero registrations — **enforced, not assumed**" with a dedicated spec ("registration during delta rollback asserts", 04-delta-snapshots.md:145-159, 300-301). Plan 5's entire A3 sequence violates that contract, and the plan text never mentions the guard, the spec, or how "legitimate rehydration registration" is distinguished from the illegal organic registration the guard exists to catch.
- **Why it matters:** By the time Plan 5 lands (it depends on 1B and 3, and likely follows 4), this is a landed, tested invariant. Worse, the distinction is not cosmetic: during rehydration, *organic* registrations still happen as constructor side effects (see B2), so a naive "guard off during rehydration" reintroduces exactly the silent uuid-drift/leak class of bug the guard was built for, violating invariant 4.
- **Fix:** Add an explicit section: a distinct `registerRehydrated(uuid)` entry point that is the *only* registration legal while `_isRollingBack`; organic `register()` continues to hard-fail; the Plan 4 spec is amended, not deleted. Define which of Plans 1B/4's asserts change and how the recovery path (`rollbackToSnapshot(beforeRollbackSnapshot)`, `GameStateManager.ts:190-199`) behaves if recreation itself throws mid-rehydration.

### B2. "Construct all missing instances unlinked" is not possible for cards, and the side-effect construction fan-out + uuid reconciliation is the actual hard problem — the plan skips it

- **Plan says:** A3 step 2 "Construct all missing instances **unlinked** (factories may need a deferred-link mode; … add a distinct rehydration entry point rather than loosening the assert)"; 5b: "recreated ability objects are matched to their serialized state records by identifier, then state is overlaid."
- **Code shows:**
  - The `@registerState` / `buildAutoInitializingCardClass` wrappers call `this.initialize()` **inside the constructor** (`GameObjectUtils.ts:263-268, 321-327`). You cannot construct a card "unlinked, initialize later": `onInitialize` runs unconditionally, and for cards it runs `setupStateWatchers` + `setupCardAbilities` (`Card.ts:382-386`, `StandardAbilitySetup.ts:25-40`).
  - That setup **constructs more GameObjects**: every `TriggeredAbility`/`ActionAbility` (constructors register organically), every ability's `AbilityLimit` (`CardAbility.ts:22` — `new UnlimitedAbilityLimit(this.game)` when no limit given), `InitiateAttackAction`, etc. Each gets a fresh counter uuid at registration.
  - Meanwhile the card's state references its abilities by their **old** uuids (`Card.ts:159-166` — `actionAbilities`/`constantAbilities`/`triggeredAbilities` are `@stateRefArray()`), and hydration goes through `getFromUuidUnsafe` → `SevereHaltGame` on miss.
- **Why it matters:** So every side-effect-constructed object must be *re-keyed* from its throwaway uuid to its old uuid: `gameObjectMapping` rekey, the single-assignment uuid assert (`GameObjectBase.ts:73-76`), and un-consuming the counter values it burned (or Plan 1B's uuid reproducibility — the stated reason Plan 5 depends on 1B — is broken by rehydration itself). A2's claim that Plan 1B means "organic post-rollback creation and rehydration cannot collide" is backwards *within* the rehydration window: an organic side-effect registration can mint `PlayerOrCardAbility_57` while another record legitimately owns that uuid, and `register()` overwrites `gameObjectMapping` **silently** (`GameStateManager.ts:93`, a hazard Plan 1B itself documents). The plan's "matched by identifier, then overlay state" sentence names the matching key for abilities only — nothing for limits (no identifier coordinate exists; the ability↔limit link is plain JS fields on **both** sides: `PlayerOrCardAbility.limit`, `PlayerOrCardAbility.ts:54`; `AbilityLimit.ability`, `AbilityLimit.ts:29`), nothing for the uuid-remap mechanics, nothing for the counter.
- **Fix:** A3 step 2 must be rewritten around reality: recreation of a composite object is "run the real constructor (links to already-live/already-recreated parents required — dependency order, ascending-numeric-uuid order is a natural candidate since it is creation order), collect all objects it side-effect-registered, match each to a record by a per-family coordinate (abilityIdentifier for abilities; ability-coordinate + role for limits; …), rekey uuids, then overlay state." Name the matching coordinate for *every* family in the recreation set, and specify the counter save/restore around the rehydration window.

### B3. The 5b recipe scheme cannot cover lasting effects, and the plan's "never survives to a snapshot boundary" carve-out is factually wrong for them

- **Plan says:** "OngoingEffect props: captured via `propertyFactory()` closures at `addEffectToEngine` time … Recipe: source card + an effect coordinate minted at registration …; recreation **re-runs the factory from the source card's definition**." Out of scope: only `then`/`ifYouDo` sub-steps and `createWithoutRefsUnsafe` transients.
- **Code shows:** Lasting effects created during ability resolution survive for a phase/round/custom duration — well past many snapshot boundaries — and their props are **resolution data, not definition data**: `CardLastingEffectSystem.ts:113` builds `{ matchTarget: card, …, ability: context.ability, ...otherProperties }` where `card` is the *resolved target* and `otherProperties` come from `generatePropertiesFromContext(context, additionalProperties)` (line 111); the `OngoingEffect` then pins these as plain readonly fields plus closures (`OngoingEffect.ts:48-57`: `source`, `matchTarget`, `condition`, `until`, `impl`, `ongoingEffect`). `until` closures in card files capture resolution objects (e.g. `GiveInToYourAnger.ts:24`, `Clone.ts:33`), and `CustomDurationEvent` construction consumes them (`OngoingEffectEngine.ts:282-297`). No "internalName_kind_idx at registration" coordinate can re-run this factory at rollback time without also serializing the resolution-captured parameters — which means either replaying resolution (impossible at a quiescent rollback point) or a parameter-capture scheme the plan does not have.
- **Why it matters:** 5b's acceptance ("rollback recreates an ongoing effect with a dynamic value") will pass on the easy case (constant-ability `persistent()` effects, which genuinely are re-derivable — `OngoingEffectSource.ts:20-54` re-runs from `buildEffectFactoryProps`) while the hard majority case is silently unsupported. Under invariant 4, "unsupported" must at minimum hard-fail — but nothing in the plan even *classifies* effects into re-derivable vs. not.
- **Fix:** Split the OngoingEffect family explicitly: (a) constant-ability effects — coordinate recipe as written; (b) resolution-created lasting effects — either declare them non-releasable/pinned (and dev-assert the classification at snapshot time, extending the plan's own "no unrecreatable object alive at snapshot time" check to this family), or design the parameter-capture recipe (serialize the resolved `matchTarget` ref, duration, and a JSON-safe parameter bag; hard-fail on closures like `until` that can't be captured). Be honest that (b)-with-capture may be Plan-7 material.

## Majors

### M1. Serialized records do not contain constructor configuration — the plan's own 5a example is not recreatable from its record

- **Plan says:** A1 factories are `classTag → (game, record, links) => instance`; 5a acceptance force-evicts "an `AbilityLimit`, a `TrackedGameCardMetric`, a token card" and asserts recreation "with identical state."
- **Code shows:** `PerGameAbilityLimit` (`AbilityLimit.ts:107-117`): `max` is a plain `readonly` constructor arg, `currentUser` is a plain *mutable* field — neither is in state; only `useCount` is decorated. Same pattern for `PerPlayerPerGameAbilityLimitBase.max` (line 146). The state system deliberately tracks only mutable-undo state, so this pattern is pervasive across the "pure-data" families the plan targets first.
- **Why it matters:** `(game, record, links) => instance` cannot supply `max`. Recreating from the record either crashes or silently produces a limit with the wrong max — the second being an invariant-4 violation that no existing test would catch.
- **Fix:** 5a must include an explicit work item: per-family audit of non-state constructor config; each field either moves into decorated state, or into the record as a "recipe" section emitted at serialize time. This is the actual bulk of 5a and should be sized as such.

### M2. Stale-JS-pointer split-brain after release/recreate — the hazard exists from 5a's first eviction, but the mitigation is scheduled in 5c and the acceptance tests can't detect it

- **Plan says:** 5c converts "the remaining hard references to state refs": `Player.playableZones`, `ZoneAbstract.owner`, `AbilityLimit.ability` "plus an audit pass."
- **Code shows:** The hard-ref surface is far larger and bidirectional: `PlayerOrCardAbility.card` and `.properties` (`PlayerOrCardAbility.ts:65-66, 109-110`), `PlayerOrCardAbility.limit` (line 54), `OngoingEffect.source/.impl/.matchTarget/.ongoingEffect` (`OngoingEffect.ts:48-56`), `CaptureZone.captor` (`CaptureZone.ts:21`, with its own STATE TODO at line 18). Plain fields are never rehydrated on rollback — only decorated fields go through `copyState`. So: evict object X, recreate X′ under the same uuid; every live object holding a plain-field pointer to X keeps using X (increments its counters, fires its handlers) while the registry, snapshots, and every state-ref hydration use X′. Silent divergence, no `SevereHaltGame`.
- **Why it matters:** This is the canonical failure mode of release-and-recreate systems, and the 5a acceptance test as specified ("recreated with identical state, working refs, functioning listeners") asserts only on the *new* instance — it would pass while the game plays against the stale one. Note the very first proposed eviction target, `AbilityLimit`, is pointed to by exactly such a plain field (`PlayerOrCardAbility.limit`).
- **Fix:** (1) Move the hard-ref→state-ref conversion for each family into the *same stage* that enables that family's release; a family is release-eligible only after its inbound plain-pointer audit is clean. (2) Add a detection mechanism to the acceptance: after eviction+recreation, sweep live objects (or use `FinalizationRegistry`/`WeakRef` in the test harness) and hard-fail if any retains the old instance identity.

### M3. uuid references embedded in `stateValue` payloads are invisible to any liveness tracking

- **Plan says:** 5c criterion (b): releasable when "no live object holds a hard reference," made enforceable by converting hard refs to state refs.
- **Code shows:** A third reference category exists: raw uuid strings inside opaque state values. `GainAbility._abilityUuidByTargetCard` is `@stateValue() Map<string, string>` of uuids (`GainAbility.ts:28, 126, 134-151` — dereferenced later via the remove-gained-ability path), and StateWatcher entries are "arbitrary `TState[]` plain objects containing `GameObjectId` strings" (Plan 3's own words, 03-codegen-serializers.md:166-168). None of these ever call `getObjectId()` at storage time on the *containing* object's behalf, so neither the `hasRef` latch nor any per-field ref graph sees them.
- **Why it matters:** Release-eligibility computed from decorated ref fields will release objects still addressed from value payloads → `getFromUuidUnsafe` → `SevereHaltGame` at an arbitrary later time; or, to be safe, the tracker must deep-scan every `stateValue` payload for uuid-shaped strings, which the plan doesn't budget for. This is also a standing-invariant-2 smell the plan half-acknowledges for GainAbility but doesn't generalize.
- **Fix:** Add a work item: inventory uuid-bearing `stateValue` payloads (the dev-mode enforcement in `StateWatcher.addUpdater` already proves they're detectable); either migrate them to real ref decorators (`stateRefMap` etc.) or make the liveness scan treat tagged-encoded `GameObjectId` strings as refs (Plan 3's JSON encoders could brand them, which would make this cheap — coordinate with Plan 3).

### M4. The headline memory target — `OngoingEffectValueWrapper` — has no recreation story, and Plan 1 already ruled out putting its value in state

- **Plan says:** 5c "release targets the churn families (**value wrappers**, expired effects, …)."
- **Code/plans show:** The wrapper's `value` is a plain non-decorated field, and Plan 1's scope constraint (01-snapshot-hygiene.md:42-61) states rollback correctness "rides on wrapper-instance *immutability plus retention*: state stores only the wrapper uuid, and the old value survives rollback because the old instance survives" — and explicitly keeps function-typed / GameObject-bearing values out of state (invariant 1). A released wrapper therefore cannot be recreated from its record: the record has no value.
- **Why it matters:** The README calls wrapper churn "the dominant memory-growth term." If wrappers can't be recreated, 5c either cannot release them (memory claim mostly evaporates, since Plan 1A only reduces, not bounds, pinning for changing dynamic values) or releases them and corrupts any old-snapshot restore that references them.
- **Fix:** 5b needs a wrapper-family recipe: JSON-safe raw values go into state (superseding Plan 1's "plain field" for that subset — Plan 1A option 1 already points this way); function/GameObject-bearing values and subclass wrappers (`GainAbility`, `AdditionalPhaseEffect`) are declared **non-releasable**, enforced by the family flag. State the residual memory bound honestly under that split.

### M5. 5c's release criterion contradicts its own acceptance test, and ignores Plan 4's delta structures

- **Plan says:** Releasable when "(a) its uuid appears in no *retained* snapshot… and (b)…". Acceptance: an object "aged out of all snapshots is verifiably absent from the registry **and recreated correctly if an old manual snapshot referencing it is restored**."
- **Contradiction:** If a manual snapshot still references it, criterion (a) forbids releasing it — in which case the acceptance scenario is unreachable; if manual snapshots are *excluded* from (a) (the only reading under which recreation-for-manual-restore is needed, and the only one that bounds memory for bookmark users), the criterion text doesn't say so, and then release is only legal for families with a *complete* recreation story — tightening the per-family flags in a way 5c doesn't spell out. Pick one.
- **Plan 4 gap:** Under deltas, "retained snapshot" must also cover: recorded old values in the global delta index (a delta chain writes old uuid refs back through field deserializers — a released referent is a `SevereHaltGame`), the pending live tracker window, and hollow current snapshots (04-delta-snapshots.md:36-40, 94-143). Plan 5's Plan-4 risk bullet covers only the "removed within the window" direction, not "released while a delta window still references it." Also 5c sweeps at `afterTakeSnapshot()` — which under Plan 4 runs per *action* delta, i.e., mid-chain.
- **Fix:** Define "retained reference set" precisely as the union of: full-snapshot records in retention windows, delta-index recorded values, pending-window records, and manual snapshots (with the manual-snapshot decision made explicitly). Capture a full record at release time if manual snapshots are excluded from pinning.

## Minors

1. **`afterTakeSnapshot()` is not "the existing hook" — it's dead code.** It is private and has exactly one reference in the tree: its own definition (`GameStateManager.ts:225-228`). The sweep needs the hook *wired* (and its interaction with the existing pre-serialize `removeUnusedGameObjects()` at `GameStateManager.ts:136-141` defined). One-line fix to the plan text, but as written it implies plumbing that doesn't exist.
2. **"The existing card factory" is an async deck-build path, not a factory.** Card construction lives in `Deck.buildCardsFromSetCodeAsync` (`Deck.ts:207-228`) and requires the full `ICardDataJson`, fetched via `await cardDataGetter.getCardBySetCodeAsync(...)`. Rollback is synchronous; a released card's `cardData` died with it. "Persist the id in the card's record" is insufficient — A1 needs a game-lifetime synchronous `id → ICardDataJson` cache (the token path already does this, `Game.ts:1583-1590`; generalize it).
3. **5c contradicts itself on tokens, and its example families cut across its own pinning policy.** "Release targets the churn families (… **dead tokens** …)" vs. two lines later "Revisit card release (defeated tokens especially) once confidence is built" — tokens are Cards, and `Card.alwaysTrackState` is true (`Card.ts:229`), i.e., pinned by the stated policy. Also `AbilityLimit` — 5a's eviction example — is itself `alwaysTrackState` (`AbilityLimit.ts:34-36`). Reconcile the family lists.
4. **`classTag` = class name becomes persistent identity in Plan 6 saves.** Invariant 2's stable-coordinate list (internalName, abilityIdentifier, enums) pointedly excludes class names; a TS class rename would silently break saved games once Plan 6 dumps these records to disk. Fine for in-memory rollback; the plan should flag the rename-sensitivity and hand Plan 6 a versioning/aliasing note.
5. **Recreation ordering left open when a cheap answer exists.** Records carry uuids whose numeric suffix is global creation order (`GameStateManager.ts:87-88`); constructing the recreation set in ascending numeric order reproduces original dependency order for the non-cyclic majority (Player before its cards, captor before its CaptureZone). Say so, and reserve deferred-link only for genuine cycles.

## Nits

- "~86 engine classes have none": I count 84 `@registerState()` occurrences across 79 files, three of which are card-file-local classes (`Bamboozle.ts`, `FirstLightHeadquartersOfTheCrimsonDawn.ts`, `Advantage.ts`) — worth noting those live under `server/game/cards/**`, which Plan 3's generator explicitly treats as territory "the static resolver can't follow" (03-codegen-serializers.md:236-238). The factory registry must not miss them.
- The `getGameObjectName` "~12 overrides" and `nextAbilityIdx`-in-state (`Card.ts:319-320`) claims verify cleanly. Credit where due: the ground-truth section of this plan is the best-verified of the set.
