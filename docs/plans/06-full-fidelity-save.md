# Plan 6 — Full-Fidelity Save/Load

**Status:** Proposed
**Depends on:** Plan 2 (schema + loader + server plumbing), Plan 3 (JSON-safe serialized records + class registry), Plan 5 (recreation from records + closure recipes)
**Shape:** Medium — most machinery exists by now; this plan is convergence and hardening.

## Goal

Grow the Plan-2 semantic save into a **complete** state capture: a saved match
restores *everything* the snapshot system knows — active duration-bound
ongoing effects, gained abilities, delayed effects, custom-duration events,
ability/effect internals — by embedding the (now JSON-safe) serialized
GameObject records and recreation recipes directly in the save file. The v1
writer's refusal list becomes empty.

Semantic save v1 and full-fidelity save are **one schema, two tiers** — not
two systems:

```jsonc
{
  "formatVersion": 2,
  // ...everything from v1 (the human-readable semantic tier)...
  "engineState": {                     // the full-fidelity tier
    "classTagsByUuid": { "...": "OngoingCardEffect", ... },
    "records": { "<uuid>": { /* JSON-safe serialized state record */ } },
    "recipes": { "<uuid>": { /* closure recipe, per Plan 5b */ } },
    "lastGameObjectId": 1234,
    "gameStateRecord": { /* Game.state record */ }
  }
}
```

The semantic tier remains authoritative for cross-version loads and human
inspection; the `engineState` tier enables exact restoration on a compatible
engine. A loader confronted with an incompatible `engineState` (schema hash
mismatch after migrations) degrades **explicitly** to semantic-tier loading
with a user-visible notice — never silently.

## Work items

### A. Writer: emit the engine tier

- Dump every registered GameObject's serialized record (Plan 3 generated
  serializers — already JSON-safe by construction), its class tag, and its
  recipe (Plan 5b) into `engineState`.
- Remove the v1 refusal list check-by-check, each with a round-trip test:
  duration-bound ongoing effects, gained abilities, delayed effects,
  custom-duration events.
- Keep writing the semantic tier from the same live game (not derived from
  records) so the two tiers cross-validate: a dev-mode check compares
  semantic-tier facts (damage, zones, counts) against the records and fails
  on mismatch.

### B. Loader: restore via recreation

- Fresh `Game` from decklists/settings (as v1), **skip semantic injection**,
  then run the Plan-5 rehydration protocol against `engineState`:
  construct-all → register (uuids from file, counter from
  `lastGameObjectId`) → deserialize records → apply recipes → `onRehydrate` →
  `afterSetState`/`afterSetAllState` → pipeline re-entry at the saved
  timepoint.
- Reconcile the objects the fresh-start path already created (Players, Zones,
  engine singletons, cards from deck build) with their records by identity
  mapping (stable coordinates → uuid), rather than duplicating them. This
  mapping is the trickiest part of the plan; the card-matching approach from
  Plan 2 (coordinates + per-copy ordinals) extends to it.
- Restore snapshot history? Optional stretch: with records being plain JSON,
  retained snapshots could themselves be persisted, letting undo survive a
  load. Recommend deferring unless cheap.

### C. Versioning & migration

- `formatVersion` bumps with a migration chain (v1 semantic-only files load
  forever; engine-tier compatibility is checked by a schema hash emitted by
  the Plan-3 generator).
- Card-data-version mismatch policy: semantic tier may load across card-data
  versions with a warning (positions reference stable names); engine tier
  requires exact match (records encode implementation-specific state).
- Lift v1's action-window-only restriction? The pipeline is still never
  serialized, so saves remain restricted to snapshot timepoints — but the
  full set (start/end of phase, regroup, setup timepoints) becomes available
  once the two `throw`ing entry points in `getEntryPointAfterRollback` are
  implemented. Evaluate demand before doing it.

### D. Hidden-information hardening

The full record dump contains deck order and both hands. Ship alongside:
- a **scrubbed export** (semantic tier only, hidden zones shuffled/omitted)
  for sharing/spectating;
- clear UX marking full saves as containing hidden information.

## Verification

- Round-trip: save → load → save produces deeply-equal documents, across a
  corpus of positions generated by running the integration suite with a
  save/load hook at every snapshot point (the undo-all-tests pattern, but
  through serialize→fresh-process→deserialize instead of in-memory rollback).
  This is the strongest available correctness oracle; budget CI time for a
  representative subset.
- Continuation equivalence: after load, scripted action sequences produce
  identical outcomes and identical subsequent save documents vs the original
  unloaded game.
- Cross-tier validation tests (semantic tier vs records).
- Degradation test: corrupted/incompatible engine tier → explicit semantic
  fallback with notice.

## Explicit non-goals

- Live migration of in-flight games across server deploys (this enables it in
  principle; productionizing it is its own project).
- Replay/event-sourcing formats.
- Cross-card-data-version engine-tier loads.

## Open questions for reviewer

- Is the two-tier design worth the writer complexity, versus engine-tier-only
  with a separate exporter for human-readable output? (Recommendation: yes —
  the semantic tier is the durable format; engine tiers age out with engine
  versions.)
- Snapshot-history persistence (B, stretch): product call.
- Where does the schema hash live — generator output vs computed at runtime
  from the registry? (Recommendation: generator output, checked at both save
  and load.)
